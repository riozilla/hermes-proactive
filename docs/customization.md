# Customization without publishing a profile

Personalization belongs in the private installed skill, existing approved memory, and local configuration—not in this repository.

| Setting | Public example | Resolve privately |
|---|---|---|
| Timezone | `{{USER_TIMEZONE}}` | Approved IANA zone and effective scheduler behavior |
| Sources | None connected | Exact accounts, scopes, pagination/freshness, unattended availability |
| Destination | None supplied | One verified private recipient and continuation route |
| Quiet hours | 23:00–07:00 proposed | Existing preferences take precedence |
| Non-urgent messages | Up to six/day, normally one hour apart | Shared quota and spacing, never a minimum |
| Discovery messages | Up to one/day | Only relevant to evidenced interests |
| Model and spending | Preserve existing | Explicit local provider, budget, and enforced controls |
| Personal interests | None supplied | User-provided preferences with provenance |
| Standing authority | None added | Exact action/resource, constraints, expiry, and revocation |

## Adjust behavior before frequency

When the agent is passive, inspect whether it has an accepted responsibility, an actual next action, usable tools, permission to prepare, and a functioning return route. Increasing ticks does not repair missing data or authority.

When it is noisy, inspect shared deduplication, source versioning, resolved-item checks, and whether a run incorrectly implies a mandatory message. Reduce low-value evaluation or communication separately; useful private work can continue without an interruption.

When it feels impersonal, give it specific preferences locally. Allow a thoughtful discovery or relevant follow-up without requiring every message to be productive. Do not infer sensitive interests or manufacture emotional knowledge.

## Event-driven extensions

A verified event source may replace some polling, but a webhook endpoint does not subscribe to an app by itself. Authenticate source events, persist signals, validate payloads, and treat content as untrusted data. Keep a clock-driven mechanism for due checks, preparation windows, and queued deliveries. Document real latency and costs.

New recurring jobs, broader permissions, new paid services, and changes to authority require approval. Prefer servicing next_check_at records through the eight existing responsibilities rather than growing an unbounded cron table.
